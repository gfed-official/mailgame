## Context

**GDD**: `design/gdd/player-character-movement.md` (P12 press, hold, channel — **counting convention superseded by ADR-0014, see below**; P11 "focus is latched while Interacting"; Game Feel "holds feel committed but forgiving"); `design/gdd/input-controls.md` (R3, R11, F2 `holdCancelRange`, H-R3-1, H-F2-1, H-G1-1, H-R4-4)
**Requirement**: `TR-movement-012` (hold counter in owner Sim ticks; one request at the held tick; no host hold timer), `TR-movement-011` (focus latched while interacting); serves `TR-input-012` (cancel range 2900 mm, hysteresis = `incumbentSlackMm`), registry-owned by input-controls
*(Requirement text lives in `docs/architecture/tr-registry.yaml` — read fresh at review time. Acceptance ids: PCM-P12-1, PCM-P12-2, PCM-P11-2c, H-R3-1 (Hold row), H-F2-1, H-G1-1.)*

**ADR Governing Implementation**: ADR-0014: Interaction framework & hold timing (§4 the hold counter, cancels; §3 release/cancel edges) — Accepted 2026-10-16 (primary); ADR-0016 (§2 `PreviewSubStep.HoldAdvance`) secondary — Accepted
**ADR Decision Summary**: Counting convention (decided in ADR-0014): `heldTicks = tick − PressTick`, evaluated after the tick's edges; the hold **completes on tick `PressTick + HoldTicks`** — a 12-tick hold pressed on tick 0 sends on tick 12 and a release edge on tick 12 (processed first) cancels. **This supersedes GDD PCM-P12-1's "press tick = held tick 1" (completion one tick earlier).** On completion exactly one request is built (`TryBuildRequest`) and sent; the hold enters `Complete` and never repeats (G6); no request carries a duration and the host has no hold timer. Cancels are checked every held tick up to and including the completion tick (after edges, before completion): release / cancel edge; chest→anchor distance² **strictly greater** than `(RangeMm + incumbentSlackMm)²` (2900 continues, 2901 cancels); anchor unregistered or `IsAvailable` false; `ShouldCancel(latch)` returning a reason; context change into Panel, Mounted or Dead; swim depth; knockdown. Walking and non-lethal damage never cancel. Each cancel records its reason in the snapshot.
**ADR Version**: ADR-0014 2026-10-16; ADR-0016 2026-10-16

**Engine**: Godot 4.7.1 .NET (Godot-free `net8.0` Sim code) | **Risk**: LOW
**Engine Notes**: None.

**Control Manifest Rules (Feature layer)**:
- Required: holds are counted only at `PreviewSubStep.HoldAdvance` (4e) in owner Sim ticks, with `heldTicks = tick − PressTick`; every edge — press, release, cancel — is resolved only in `PreviewSubStep.EdgeResolve` (4d), which runs before accrual in the same tick (ADR-0016 §2 Implementation Guidelines, "Edges must be resolved only in `PreviewSubStep.EdgeResolve`"; manifest Forbidden "never resolve an edge outside `PreviewSubStep.EdgeResolve`"); the cancel range is `RangeMm + incumbentSlackMm`, compared strictly on squared distances; the host never times a hold or receives a duration (ADR-0014 §4)
- Forbidden: re-targeting a hold to the current focus; timing holds on the host (ADR-0014 Alts 1, 3); resolving a release or cancel edge inside `HoldAdvanceStep` (ADR-0016 §2 — see Implementation Notes, TD-186 item 1)

*From GDD PCM-P12-1/2, PCM-P11-2c and input-controls H-R3-1 (Hold row), H-F2-1, H-G1-1, H-R4-4, scoped to this story. - [x] **PCM-P12-1 (ADR convention).** a 400 ms hold (12 ticks) pressed on tick 0 sends exactly one request on **tick 12**, none on tick 11; a release edge on tick 12 (processed before accrual) cancels with no request; **hold-as-toggle** (logical press at tick 0, the router's second press arrives as a cancel/release edge) produces the identical request on tick 12 and a second press before then cancels. ## Implementation Notes

*Derived from ADR-0014 §3–§4:*

- Files in `src/PerformativeMail.Sim/Players/Client/`: `HoldAdvanceStep.cs` (new; `IClientStep` bound at `PreviewSubStep.HoldAdvance`, 4e), `HoldCounter.cs` (pure state transition: `(state, tick, ctx) → (state', action)`). **No new `CancelReason.cs`:** `CancelReason` is the as-built `byte` enum in `src/PerformativeMail.Sim/Players/InteractionGate.cs:13-38` (`None = 0, Panel = 1, Mounted = 2, Dead = 3, Swim = 4, Knockdown = 5, Unavailable = 6, Busy = 7`); this story appends `Released = 8, OutOfRange = 9, Unregistered = 10, OwnerCancel = 11` (append-only local enum, not a shared id space). `OwnerCancel` cannot carry a `StringId` as an enum member: the hook's reason key travels in `InteractionStatus.LastCancelReason` (`Players/Client/InteractionStatus.cs`). Context changes use the existing `Panel / Mounted / Dead / Swim / Knockdown` returned by `InteractionGate.ContextCancelReason` (`InteractionGate.cs:217`). Update the value pins at `tests/unit/player/InteractionGateTests.cs:521-528` with the four new rows.
- **Release/Cancel edges are resolved in `EdgeResolveStep` (4d), in arrival order interleaved with presses — not in this step** (Mail Lead planning default, approved by Evan 2026-10-29 7:41 AM PT (TD-186 item 1)). As the story was written they were processed at 4e, which would break ADR-0016 §2 ("Edges must be resolved only in `PreviewSubStep.EdgeResolve`") and the manifest's Forbidden rule; this default changes the story, not the ADR. As built, `EdgeResolveStep.Step` walks only `EdgeKind.Press` (`Players/Client/EdgeResolveStep.cs:97-108`) and `PressResolver` returns `Ignored` while Holding, which is TD-171's open item A9 (a frame "Press A, Release, Press B" ignores B); this story adds the Release/Cancel branch there: end a Channel with `ICatchArmSender.Send(down: false)`, cancel an incomplete Hold with `CancelReason.Released`, return `Complete` to `Idle` — closing TD-171 A9 without an erratum. ADR-0014 §4's "a release edge on tick 12 (processed first) cancels" still holds because 4d precedes 4e. There is no shared `EdgeCursor`: `ClientStepContext` is a readonly struct with an internal constructor owned by simulation-core (`src/PerformativeMail.Sim/ClientLayer/ClientStepContext.cs:20-24`) and nothing named `EdgeCursor` exists in src. `HoldAdvanceStep` (4e) owns accrual, the non-edge cancel list, completion, the counters and `FocusState.Latched`; `tests/unit/player/EdgeResolveAllocationTests.cs:13` (0 B for `EdgeResolveStep`, advisory) must still hold after the release handling is added.
- Per held tick, in this order: (1) this tick's release/cancel edges were already applied at 4d (above), so a hold still `Holding` here survived them; (2) evaluate cancel conditions: distance² via chest point of the *current* `CarrierState` vs `(RangeMm + incumbentSlackMm)²` in `long`, then registry/availability (`AnchorRegistry.TryGet` / `DefAt` / `ImplAt`, `Players/AnchorRegistry.cs:233, 265, 272`), `ShouldCancel`, then context/swim/life: the step keeps the previous tick's `CarrierStatus` (read through `ICarrierFocusSource.Status`) and calls `InteractionGate.ContextCancelReason(previous, current)` once per held tick — it yields `Swim` on the swimming false → true edge and `Knockdown` on `Alive → Dead`, plus `Panel` / `Mounted` / `Dead` (Story 013); (3) if not cancelled and `tick == PressTick + HoldTicks` → complete (build + send exactly once); (4) otherwise leave Holding. Progress = `Hold.ProgressPm(tick − PressTick, HoldTicks)` (`Players/Hold.cs:84`, already shipped) published by Story 018. `HoldAdvanceStep` reaches the interaction through `EdgeResolveStep.Interaction` (`ref InteractionStatus`, `EdgeResolveStep.cs:93-94`) and the focus through `FocusStep.State` (`Players/Client/FocusStep.cs:75`), by constructor, plus `ICarrierFocusSource`, `AnchorRegistry`, `PlayerSettings`, `ICatchArmSender`, `IRequestSink`, `SimCounters`, `SimCheckRing` and `PlayerSlot`. `tests/unit/player/PressResolutionTests.cs:538` pins `Latched == false` after a hold press in a rig that binds only Focus and EdgeResolve: it stays valid because `Latched` is set at 4e, not 4d.
- Channel anchors owned by other systems (Belt `Push`, M-1b) need a start/stop request builder that `IInteractable` (ADR-0014 Key Interfaces) does not declare — **ADR gap flagged, scoped to M-1b**: at M-1a only the Catch channel (through `ICatchArmSender`) is implemented; a Channel-mode anchor press latches the state and sends nothing, recording `CheckCode.ChannelAnchorNoBuilder = 16` (`src/PerformativeMail.Sim/Core/CheckCode.cs` ends at `InventoryConservationMismatch = 15`; `SimCheckRing.Record(code, tick, a, b)`, `Core/SimCheckRing.cs:106`; `SimCheckRingTests` derive the max code dynamically, no pin on 16) — Mail Lead planning default, approved by Evan 2026-10-29 7:41 AM PT (TD-186 item 3). The ADR-0014 amendment for a Channel start/stop builder stays an M-1b follow-up before Push is implemented; it does not block this story.
- Busy sink: ADR-0014 is silent on a `TrySend == false` at completion; the conservative choice (cancel with `Busy`, no retry, so one press never double-sends; it matches Story 016's as-built refused `Send(down: true)` → `Busy`) is Mail Lead planning default, approved by Evan 2026-10-29 7:41 AM PT (TD-186 item 2), recorded in the TD-186 register row and the decision log entry of 2026-10-29.
- Clearing (TD-171 A8): `LastCancel` and `LastCancelReason` are cleared on the next successful latch or Tap send — this story touches `EdgeResolveStep` under item 1 anyway (Mail Lead planning default, approved by Evan 2026-10-29 7:41 AM PT (TD-186 item 5)).

No `SimAssertCode`, `SectionIds`, `EventKind` or `OpKind` (requests are the owner's ops via `TryBuildRequest`; client state is not dumped).
