**ADR Decision Summary**: Drop spawns one WorldItem (`origin = Dropped`) at the player's position + 500 mm along facing, snapped to the nearest ground tile (water → floats 10 s then returns/destroys; inside non-walkable geometry → the player's own position); rejected while swimming (`swimming`) (GDD R7 drop row). Under the ADR-0009 erratum of 2026-10-29 the handler is Player Character's (`Players/Ops/DropHandler.cs`, kind `0x0040` in the Players block), mirroring the `DeliverMatching` ownership erratum of 2026-10-16: it reads the pose through a Players-internal seam, asks `IWorldQuery` for the drop point and calls the one Inventory primitive `IInventoryApi.DropEntry(slot, entry, posMm, onWater)`, which does the atomic whole-entry lift through the mutator and story 013's `CreateWorldItem` in one call scope (like `TryCatch`). The ground/water/walkability query is `IWorldQuery` (ADR-0026 §3–§4); the pose, facing and swim state are the carrier solver's (ADR-0013).
**ADR Version**: ADR-0009 2026-10-16 (erratum 2026-10-29); ADR-0026 2026-10-16; ADR-0013 2026-10-16

**Engine Notes**: None — nothing Godot-facing; the WorldItem's presentation is grid-inventory 023's.

## Acceptance Criteria

*From GDD `design/gdd/grid-inventory.md` (test IDs `H-…`), scoped to this story:*

- [ ] **H-R7-4 (drop half)** — `isSwimming = true` and a letter on the cursor → `drop` → `ok:false, swimming`, no WorldItem, nothing mutated, no record; `isSwimming = false` → exactly one WorldItem `origin = Dropped` at position + 500 mm along facing, snapped per the drop-point rule below, `expiresTick = tick + 9000`; the reply follows the entry's container records and its one `InvVersion` seal, then `WorldItemSpawned`.
- [ ] **Atomic lift-and-drop** — a focused-cell drop (panel entry, no `pick` first) and a cursor drop are each one `DropEntry` call: the whole entry leaves its container and becomes the WorldItem in one call scope (one seal per touched container, +1); a refusal inside `DropEntry` (`stale_entry`, `container_gone`) changes nothing (the primitive's own contract, ADR-0009 Key Interfaces; whether the handler's `Commit` can ever see one is the open item in "The handler" below, not settled here). A drop point on water floats (story 013 water class, `onWater = true`); a point inside non-walkable geometry uses the player's own position.
- [ ] **Drop point (`GI020-SNAP-1`)** — Mail Lead planning default, approved by Evan 2026-10-29 9:07 AM PT (TD-192 item 1): the +500 mm point is first clamped inside the map with the 1000 mm inset (`ClampInsideMap`); if `WaterDepthMm` there is > 0 the item floats there at y = 0 with `onWater = true`; else if the tile is `Walkable` the item lands at `TerrainHeightMm`; else `TrySnapWalkable` with radius `WorldConstants.TileSizeMm` (2000) and `TerrainHeightMm` at the snapped point; else the player's own position. Tests: a deep-water point floats (not snapped to the shore tile); a shallow (< 900 mm) point still floats (water wins over `Walkable`); a `Blocked` tile with a `Walkable` neighbour inside 2000 mm snaps; a `Blocked` tile with none falls back to the player's position; a point past the map edge is clamped first. `Tile(...).Water` is never read.
- [ ] **Facing (`GI020-FACE-1`)** — Mail Lead planning default, approved by Evan 2026-10-29 9:07 AM PT (TD-192 item 2): the drop point is `(x + ((500 · fx) >> 10), z + ((500 · fz) >> 10))` with `(fx, fz) = FocusScore.Forward(BodyYaw)` (Q10, `Players/Client/FocusScore.cs:51-55`; ADR-0013 l.89 forward = (−sin θ, −cos θ)); a yaw-0 drop lands within 1 mm of `(x, z − 500)` and a yaw-16384 drop within 1 mm of `(x − 500, z)`; no float, no division.
- [ ] **Reason precedence (`GI020-PREC-1`)** — Mail Lead planning default, approved by Evan 2026-10-29 9:07 AM PT (TD-192 item 3): one ordered chain `bad_request → swimming → not_open → stale_entry | container_gone` (`swimming` is checked in `Validate` from the pose seam; `stale_entry` or `container_gone` is decided at id resolution by the tombstone lookup), covered by ADR-0009's parametrised precedence test (a request violating every later rule asserts the earliest code). How `Validate` reaches the last three codes is the open item in "The handler" below.
- [ ] **Composition and kind (`GI020-COMP-1`)** — `PlayersSystem`'s constructor takes `IInventoryApi`; Players binds the `Drop` descriptor (`OpKind` `0x0040`, 4 B `DropPayload`, reasons `not_open`, `stale_entry`, `swimming`, `container_gone`); `InvOpDescriptors.All` is eight kinds; `CompositionRulesTests` and the construction-order pin (`SimCompositionTests.cs:449`) stay green; a `SimProfile` without Inventory leaves Players' Drop unbound (no `UndeclaredDependency`).

## Implementation Notes

*Derived from the governing ADR(s) Decision / Implementation Guidelines:*

- **Ownership (ADR-0009 erratum 2026-10-29; the handler move approved by Evan 2026-10-29 7:41 AM PT, the `OpKind` renumbering 9:07 AM PT).** The story as first written read pose, facing and swim state "from `IPlayersApi`" — which exposes no pose read (`src/PerformativeMail.Sim/Players/IPlayersApi.cs:11-43`: life state and anchor registration only); Inventory may inject an `I…Api` only for a declared dependency (ADR-0003 §4; `tests/unit/architecture/CompositionRulesTests.cs:577`), and `SystemGraph.cs:50` declares Player Character → Grid Inventory with Grid Inventory depending on nothing (`SystemGraph.cs:66-67`), so the reverse edge is a cycle (construction order pinned at `tests/unit/sim/Composition/SimCompositionTests.cs:449`). Resolution, mirroring the `DeliverMatching` ownership erratum (ADR-0009 l.356): the handler is `src/PerformativeMail.Sim/Players/Ops/DropHandler.cs`, bound by Players; `PlayersSystem` gains an `IInventoryApi` constructor parameter (`PlayersSystem.cs:61`; call site `Composition/SimComposition.cs:193`; `Players → GridInventory` is declared, so `CompositionRulesTests` passes it). `Drop` moves with its descriptor and `DropPayload` from the Inventory block (`0x008A`, `Inventory/Ops/InvOpKinds.cs:48`, `InvOpPayloads.cs:102-108`) to the Players block as **`0x0040`** (`Core/OpKindBlock.cs:40`; the block has no registered kind, `Core/OpKind.cs:21-30`), exactly as `DeliverMatching` moved to the Delivery block; `0x008A` retired as an `OpKind` (`EventKind` 0x008A `BacklogUnits`, `Inventory/Events/InvEventKinds.cs:47`, is a separate table, unaffected). The renumbering itself: Approved by Evan 2026-10-29 9:07 AM PT, Mail Lead chat, in his own words answering Mail Lead's card 'Grid-inventory 020 (PR 61), corrected: approve the Drop op id move (0x008A to 0x0040) and the TD-192 defaults, with rejection order bad request, swimming, not open, then stale entry or container gone?': "Approve moving Drop's op id from 0x008A to 0x0040 in the Players block, and all three TD-192 defaults for grid-inventory 020 with the corrected order: bad request, swimming, not open, then stale entry or container gone".
- **The Inventory primitive.** `IInventoryApi.DropEntry(PlayerSlot slot, EntryId entry, Vec3Mm posMm, bool onWater)`: resolves the entry (the actor's cursor or an open panel container; `not_open`, `stale_entry`, `container_gone` as the Inventory-side refusals), lifts the whole entry through `InventoryMutator` and calls `CreateWorldItem(entry, posMm, WorldItemOrigin.Dropped, onWater, now)` in one call scope, like `TryCatch` (`IInventoryApi.cs:273`; `CreateWorldItem` at `:219`): the container records and one `InvVersion` seal first, then `WorldItemSpawned` in `CreateWorldItem`'s nested scope with story 013's cap eviction. Its result (the WorldItem id and a reason; reason 0 = dropped, else refused and nothing changed) is this story's to fix as built (ADR-0009 Key Interfaces, erratum 2026-10-29). `InventoryMutator.cs` gains a lift primitive only if the existing ones cannot express the whole-entry lift.
- **The handler.** `Validate` (pure), in the TD-192 item 3 order as approved by Evan 2026-10-29 9:07 AM PT: `bad_request` (namespace/high-water per `InvRequestCheck`), then `swimming` from the pose seam (`LocoState.Swimming`), then `not_open`, then `stale_entry` or `container_gone` (the tombstone lookup decides which). `Commit`: compute the drop point (TD-192 items 1–2), call `DropEntry` once, build the reply.
  **Open (Mail Lead, PR #61 r2): unresolved.** As this story stands, `Validate` has no way to reach the last three checks. `IInventoryApi` (`src/PerformativeMail.Sim/Inventory/IInventoryApi.cs`) has no read-only entry-resolution or open-state member — its members are `Spawn` (l.168), `PeekOutfeed` (l.180), `TakeUnit` (l.192), `CreateWorldItem` (l.219), `ConsumeUnit` (l.232), `DetachForThrow` (l.251), `TryCatch` (l.273), `TryInsert` (l.288), `CountItem` (l.299), `WeightPoints` (l.310), `SpeedPermille` (l.319), `AppendBacklog` (l.333) and `BacklogUnits` / `BacklogEntries` — and `InvRequestCheck`'s `not_open` / `stale_entry` / `container_gone` checks (`InvRequestCheck.cs:140, 210-211`) run over Inventory's own tables, which Players cannot reach. So, as the story is written, those three reasons could only surface from `DropEntry` inside `Commit`, which conflicts with ADR-0009 §2 l.235 ("a pure `Validate` and a never-failing `Commit`"). No `IInventoryApi` member or read is proposed here, and this note claims neither that `Commit` can be refused nor that it never fails. **This story must not be built until Mail Lead and Evan settle how `Validate` reaches `not_open`, `stale_entry` and `container_gone`** (Mail Review PR #61 r1 B1; decision log 2026-10-29 9:07 AM PT entry).
- **Pose seam (Players-internal).** Feet, `BodyYaw` (ADR-0013 l.74; l.238: the Sim value is used for the drop position) and swimming are read from `PlayerRecord.Carrier` (`Players/PlayerRecord.cs:35` — the seeded spawn pose; the host never steps an Alive player's carrier) at M-1a; swimming is `LocoState.Swimming` (`Players/LocoState.cs:14`). Once player-character 019 lands, the seam reads the ingested host position and the sample's `Swimming` bit instead (story 019's `HostPositionTable` and `SampleFlags`) — a one-site change; 019 is **not** a dependency of this story (the `PlayerRecord.Carrier` stand-in is the erratum's M-1a form).
- **Drop point** (Mail Lead planning default, approved by Evan 2026-10-29 9:07 AM PT, TD-192 item 1): `ClampInsideMap(p, 1000)` (ADR-0026 l.90) → `WaterDepthMm > 0` → float at y = 0, `onWater = true` → else `Tile(p).Walkable` → `TerrainHeightMm` → else `TrySnapWalkable(p, WorldConstants.TileSizeMm, out snapped)` (`World/WorldConstants.cs:10`; ADR-0026 l.91) → else the player's own position. The GDD's "snapped to the nearest ground tile, if that tile is water the item floats" cannot be read literally: `TrySnapWalkable` returns only `Walkable` tiles and `Walkable` requires `WaterDepthMm < 900` (ADR-0026 l.87), so the water test comes first. Water authority: `WaterDepthMm`, never `Tile().Water` (ADR-0026 l.180).
- **Facing** (Mail Lead planning default, approved by Evan 2026-10-29 9:07 AM PT, TD-192 item 2): `FocusScore.Forward(BodyYaw, out fx, out fz)` (`Players/Client/FocusScore.cs:51-55`) and an arithmetic shift, `x + ((500 · fx) >> 10)`, `z + ((500 · fz) >> 10)`; no new trig.
